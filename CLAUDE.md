## Architecture

This is a Flutter app that links phones over BLE so that other Android apps can exchange data with the same app on a paired phone (AIDL), and later control the peer (remote media keys). Every device can act as a peripheral (advertising) and as a central (scanning and connecting). All BLE and protocol work happens in native code, because it must run without Flutter. Dart only manages connections and app pairing, over two platform channels. The wire protocol is specified in `docs/protocol.md`; the text chat it was first tested with has been removed (the AIDL test app in `test_app/` replaces it).

### Platform channel contract (keep all three sides in sync)

- **MethodChannel** `com.rouddy.bluetooth_communicator/bluetooth_control`. Methods: `initialize`, `setAdvertisingEnabled{enabled}`, `setCentralEnabled{enabled}`, `scanNow`, `connectDevice{deviceId, pair}`, `removeDevice{deviceId}`, `respondPairing{deviceId, accept}`.
- **EventChannel** `com.rouddy.bluetooth_communicator/bluetooth_events`. Each event is a flat map with a `type` key: `status{advertising, scanning, connectedCount, bluetoothOn}`, `discovered{deviceId, name}`, `connected{deviceId, peerId, name}`, `disconnected{deviceId}`, `peers{peers: [{deviceId, peerId, name, platform, state, connected}]}`, `pairingRequest{deviceId, peerId, name, code, repair}`, `pairingResult{deviceId, peerId, result}`, `peerRejected{deviceId, reason, byPeer}`, `peerUnpaired{deviceId}`, `bonding{deviceId}` (Android only, emitted when `createBond` starts), `bondLost{deviceId}` (the OS pairing was removed on either phone; shown as 페어링 해제됨 until it connects again), `error{message}`.
- `connected` means an authenticated protocol session (docs/protocol.md 6.1), not a GATT connection; `name` is the one the peer announced in HELLO. `disconnected` is sent when no session to that device is left, and also when a connect attempt ends without one (so Dart can leave 연결 중).
- `peers` is the full list of app-paired peers, which native code owns (Android: `ble_identity` prefs + Keystore). It's sent on `initialize` and whenever it changes; Dart's 연결 기록 list is built from it and isn't persisted in Dart. `state` is `paired`, `repairNeeded` (the peer answered UNKNOWN_PEER), `badMac`, or `unpairedByPeer`. Only `paired` peers are reconnected automatically.
- App pairing (6.3): when the user connects with `pair: true` to a phone this app has no key for, both phones get `pairingRequest` with the same six-digit `code`, and each user answers with `respondPairing`. An approved request stays pending until the peer approves too; `pairingResult.result` is `paired`, `rejected`, `timeout`, `cannotPrompt`, `mismatch`, `badMac`, or `linkLost`. Pending requests are replayed on `initialize`. Android posts a notification for them when the app isn't in the foreground.
- `peerRejected.reason` is the REJECT reason in lowerCamel (`unknownPeer`, `badMac`, `alreadyConnected`, …). `alreadyConnected` is never sent to Dart (it's routine, 9절).
- `removeDevice` sends UNPAIR if a session is up (waiting at most 3 s for its ACK), deletes the key and the peer, and then drops every link to the device and cancels pending connects. The peer gets `peerUnpaired` and stops reconnecting.
- Shared GATT UUIDs are hard-coded on both native sides. Service `1F9ED31D-B738-4D4C-A6D8-86DBF0F9C001`; protocol characteristic `002069AC-115D-4391-8772-13E44DF757FC` (changed from the chat's `DB912050-…` so old builds don't connect). It carries protocol frames: the central writes with response, the peripheral notifies.
- Both sides send the same structured `status`, and Dart builds the label (`advertising scanning connected:1`, `idle`, `bluetooth-off`; `unknown` before the first event). `connectedCount` counts peers with a session.
- `initialize` returns a Bool on both platforms. Android returns `true` once it has started the background service, or `false` if the Bluetooth permissions are missing. iOS returns whether the Bluetooth authorization is `allowedAlways`. Runtime permissions aren't part of the channel contract: Dart requests them with `permission_handler` before calling `initialize`.
- `pair` is true only for user-initiated connects (the 연결 button). Android then bonds unbonded devices first via `createBond()` (system pairing dialog), and only such links may start an app pairing. Without it, Android connects only to bonded app-paired peers, so automatic reconnects never prompt. iOS ignores it.
- `deviceId` is the MAC address on Android and the `CBPeripheral.identifier` UUID string on iOS. These IDs are not portable between platforms; `peerId` (a UUID per install) is.

When you add a method or event, update `lib/main.dart` (`BleAppController._invoke` / `_handleEvent`), `MainActivity.kt` + `BluetoothBackgroundService.kt` (+ `BleRuntime.onDartEvent` for engine events), and `AppDelegate.swift`.

### Dart (`lib/main.dart`, single file)

- `BleAppController` is a `ChangeNotifier`; each page listens to it (`ListenableBuilder`). It keeps the advertising/central toggles in `shared_preferences` and replays them on `initialize()`; the registered-device list comes from the native `peers` event. Keys from older builds (`prefs_messages`, `prefs_unread_counts`, `prefs_registered_devices`) are deleted on launch.
- Permissions: `BleAppController.checkPermissions`/`requestPermissions` use `permission_handler`. Required permissions are `bluetoothScan`/`bluetoothConnect`/`bluetoothAdvertise` on Android and `bluetooth` on iOS. `notification` is requested on Android but stays optional (it's used for pairing requests in the background). If the user permanently denies a permission, the settings page offers `openAppSettings()`. Once the Bluetooth permissions are granted, the settings page shows them as a status that can't be tapped, plus a separate tile that opens system settings while notifications are off (`notificationsDenied`). While the settings page is open, coming back to the app re-checks the permissions (`refreshPermissions`) and runs `initialize()` if they were just granted. On iOS (Swift Package Manager build), permission_handler enables `PERMISSION_BLUETOOTH` from the `NSBluetoothAlwaysUsageDescription` key in `Info.plist`, so there's no Podfile macro to set.
- `HomePage` shows the device list (app-paired peers and connected devices under 연결 기록, scan results under 주변 기기). `DeviceControlPage` (link state, connect button, peer ID, delete) is pushed from it. `SettingsPage` is pushed from the home app bar. `MyApp` shows a `PairingDialog` (code, 승인/거절, then "waiting for the peer") for each `pairingRequest`, on whatever page is open; it closes itself when the request ends. Errors, pairing failures, and rejections show as SnackBars. The UI strings mix Korean and English.

### Android (`android/app/src/main/kotlin/.../bluetooth_communicator/`)

- `minSdk` is 31 (Android 12), so the app only uses the `BLUETOOTH_SCAN`/`CONNECT`/`ADVERTISE` runtime permissions and has no location-permission or pre-Oreo code paths. The remaining `SDK_INT` checks are for API 33 (`TIRAMISU`) GATT/parcel APIs.
- `compileSdk` is pinned to 37 because `permission_handler_android` 14.x requires it. `targetSdk` still follows Flutter's default.
- `protocol/` is the protocol of `docs/protocol.md`, in plain Kotlin with no Android dependencies, tested on the JVM (`android/app/src/test/.../protocol`, including `EngineTest`, which connects two engines through an in-memory network on a virtual clock): `Frames` (split by MTU, at most 512 bytes per frame; reassemble per tid), `Records`/`Envelopes` (encodings, TLV), `Crypto` (SHA-256, HMAC, HKDF, AES-GCM, P-256 ECDH, replay window), and `ProtocolEngine`. The engine runs every link: frame scheduling by priority, HELLO, app pairing, AUTH, SEALED sessions, one link per peer, and delivery (ACK, dedup, retransmission, TTL, flow control, CAPS, UNPAIR). It isn't thread-safe; everything calls it on the main looper.
- `BleRuntime` is a process-wide singleton: it owns the engine, the `AndroidPeerStore` (peerId, msgId counter, and peers in `ble_identity` prefs, excluded from backups by `data_extraction_rules.xml`; each pair key K is imported into the Android Keystore as an HMAC key, with a logged prefs fallback if the import fails), and the `AppRegistry`. It implements the engine's host: frames go to the transport (the BLE service while it runs), engine events become Dart events, pairing notifications (channel `ble_pairing`), and `peers` snapshots for AIDL.
- `MainActivity` doesn't touch BLE or request permissions. It turns each method call into an `Intent` action (`ble.action.*`) and sends it to `BluetoothBackgroundService` with `startForegroundService`.
- `BluetoothBackgroundService` is a `START_STICKY` foreground service (`connectedDevice` type). It owns advertising (plus the GATT server, opened and closed with it), scanning, and GATT client connections, and carries the engine's frames: a client link starts when its CCCD subscription succeeds, a server link when a central subscribes. GATT callbacks post their work to the main looper. Connections go through bonding: an unbonded device is bonded first (`bondStateReceiver` waits for `BOND_BONDED`) and then connected. User-initiated connects go direct (`autoConnect=false`); automatic ones use `autoConnect=true`, target only bonded peers the engine wants (`shouldReconnect`: app-paired, state `paired`, no live link), and are spaced at least 10 s apart per address. It saves its own toggle state in `ble_service_prefs`, separately from Dart's prefs, so it can restore that state without Flutter running.
- Bonding is what keeps `deviceId` stable. Unbonded phones advertise with rotating random addresses. Once bonded, the stack resolves every later advertisement and incoming connection from that phone to the address it had at bonding time. So scan results, client links, and GATT server peers all report the same ID.
- Two phones with central mode on usually connect to each other twice. The engine keeps one link (9절): it decides when the second link's HELLO arrives, and an established link wins only if it answers a `/ping` within 3 s. Samsung's own services keep the Bluetooth connection up after our app dies, so a dead session otherwise looked alive. The client also re-handshakes on `onServiceChanged` (the peer re-registered its GATT server).
- A client connection whose link the engine dropped while the peer stays linked to our GATT server is kept open, unused (`idleClients`): Android releases the shared connection once no app on the phone holds it as a GATT client, which took the remaining link down. It's reused or closed when that link ends. The ATT MTU is per connection, so both roles use the MTU either side learned (`attMtu`): a central subscribing over an existing connection doesn't renegotiate it.
- The service listens for `BluetoothAdapter.ACTION_STATE_CHANGED`. On power-off it resets its state and drops every link, and the status becomes `bluetooth-off` (iOS reports the same string, and Dart shows a banner). On power-on it runs `restoreStateFromPrefs()`. Each advertising start uses a new `AdvertiseCallback`. The framework keeps the old one across a power cycle, and reusing it fails with `ALREADY_STARTED`. `advertiseCallback != null` marks a start in progress, so overlapping start requests don't create a second advertising set.
- GATT operations run through `GattOperationQueue`, one queue per link and role (`clientQueues`, `serverQueues`). Android allows a single outstanding operation per connection, so the CCCD write, frame writes, and notifications each wait for their callback (`onDescriptorWrite`, `onCharacteristicWrite`, `onNotificationSent`). When a link goes away, its queued operations fail.
- `BluetoothBootReceiver` sends `ACTION_RESTORE` on boot.
- `BleEventBus` is a process-wide singleton. It posts events to the Flutter `EventSink` on the main looper, and drops them without a sink (`initialize` replays the state: `BleRuntime.replay`). `MainActivity.cleanUpFlutterEngine` detaches the sink, because the engine dies with the activity without calling `onCancel`. `appInForeground` (onResume/onPause) decides whether a pairing request posts a notification. Resuming clears those notifications.
- **AIDL** (`android/app/src/main/aidl/com/rouddy/bluetooth_communicator/api/`, 11절): `BleCommunicatorService` is exported with action `com.rouddy.bluetooth_communicator.action.BIND`, no permission. `IBleCommunicator` declares the actions, the package, and the result codes as constants. Callers are identified by `Binder.getCallingUid()`: a path must start with one of the caller's packages, and an app is (package, SHA-256 of its signing certificates). `AppRegistry` keeps the listeners, builds our CAPS from them and from apps that declare an `action.RECEIVE` service (refreshed on package changes), checks incoming messages against the sender's CAPS and the local certificate, and delivers them to a listener or by binding the RECEIVE service. `getPeers` only lists peers whose CAPS have the caller's app. The manifest's `<queries>` lists the RECEIVE action for package visibility.

### test_app (`test_app/`)

A standalone Android app (own Gradle build, AGP 9 built-in Kotlin, no AndroidX) that compiles the communicator's `.aidl` files directly. It lists peers, sends text to `<its package>/chat`, and shows each result; a `ReceiveService` takes messages while the activity is closed. `adb shell "am start -n com.rouddy.bluetooth_communicator.testapp/.MainActivity --es text '…'"` sends to the first connected peer, and results are logged under `TestApp`. Both phones need APKs signed with the same key.

### iOS (`ios/Runner/AppDelegate.swift`)

- `IOSBleBackgroundManager` handles the channel stream directly and owns a `CBCentralManager` and a `CBPeripheralManager`. Both use state-restoration identifiers, and `UIBackgroundModes` includes `bluetooth-central` and `bluetooth-peripheral`. It saves its toggles in `UserDefaults` (`pref_ios_advertising`, `pref_ios_central`).
- Peripheral role: `IOSBleBackgroundManager` publishes a `CBMutableService` with the message characteristic (write, writeWithoutResponse, notify) and starts advertising from `didAdd`. Writes become `message` events, and a subscription becomes `connected`. `sendMessage` to a subscribed central uses `updateValue`, queueing when the transmit queue is full until `peripheralManagerIsReady`. Turning advertising off removes the service, and Bluetooth power-off resets the peripheral state.
- Central role: `connectDevice` falls back to `retrievePeripherals(withIdentifiers:)` for saved devices that weren't scanned in this launch. Requests made before the manager is `poweredOn` wait in `pendingConnectIds`. `connected` is emitted when the notification subscription succeeds, not on `didConnect`. When the peer requires encryption, the first subscribe fails with insufficient authentication/encryption: iOS starts pairing but doesn't retry, so the subscribe is retried every 2 s, up to 30 times.
- The app uses the UIScene lifecycle (`SceneDelegate.swift`). So `window` is still nil in `didFinishLaunchingWithOptions`, and both the plugins and the BLE channels are registered in `didInitializeImplicitFlutterEngine` (`FlutterImplicitEngineDelegate`) on `engineBridge.applicationRegistrar.messenger()`.

## Current state / known gaps

Branch `feature/bluetooth_protocol`. On Android, the protocol of `docs/protocol.md` is implemented through step 5 plus AIDL (step 7): framing, app pairing, AUTH, SEALED, one link per peer, delivery, CAPS. Verified between two Galaxy phones (Z Fold5 and S23, Android 17): app pairing from either phone and declining it, reconnects after a force-stop and a Bluetooth power cycle, deletion with UNPAIR, and the test app in both directions (listener and RECEIVE service, 3000-byte messages, delivery after the peer's Bluetooth came back). Keep these gaps in mind:
- **iOS isn't ported.** `AppDelegate.swift` still speaks the old raw-UTF-8 chat on the old characteristic, so iOS can't talk to the new Android build, and the new channel methods (`removeDevice`, `respondPairing`) aren't implemented there. Porting means the codecs, crypto (CryptoKit), and engine in Swift, against the same JVM test cases.
- Step 6 (`/control/media`, remote media keys) isn't implemented; built-in paths answer UNSUPPORTED, except the engine's own `/ping`.
- A peripheral link whose peer app died stays "established" until that peer connects again or Bluetooth disconnects. If the peer then has central mode off, this phone doesn't reconnect either (`shouldReconnect` sees the live link).
- `GattOperationQueue` has no timeout: a GATT callback that never comes stalls that link's frames (messages then expire by TTL).
- On both platforms the protocol characteristic and its CCCD require an encrypted link. An unbonded central gets "insufficient encryption" (iOS centrals then pair automatically) instead of talking under a rotating random address.
- `BLUETOOTH_SCAN` must keep `neverForLocation`. Without it, Android 12+ silently delivers zero scan results because the app doesn't hold location permission.
