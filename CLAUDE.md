## Architecture

This is a Flutter app that links phones over BLE so that other Android apps can exchange data with the same app on a paired phone (AIDL), and later control the peer (remote media keys). Every device can act as a peripheral (advertising) and as a central (scanning and connecting). All BLE and protocol work happens in native code, because it must run without Flutter. Dart only manages connections and app pairing, over two platform channels. The wire protocol is specified in `docs/protocol.md`; the text chat it was first tested with has been removed (the AIDL test app in `test_app/` replaces it).

### Platform channel contract (keep all three sides in sync)

- **MethodChannel** `com.rouddy.bluetooth_communicator/bluetooth_control`. Methods: `initialize`, `setAdvertisingEnabled{enabled}`, `setCentralEnabled{enabled}`, `scanNow`, `connectDevice{deviceId, pair}`, `removeDevice{deviceId}`, `respondPairing{deviceId, accept}`, `requestClipboard{deviceId}`, `setClipboardSharing{enabled}`, `controlMedia{deviceId, op}`, `sendFile{deviceId, path?}`, `respondFile{id, accept}`, `cancelFile{id}`, `dismissFile{id}`, `exportFile{id, action}`, `setDeviceName{name}` (iOS only: since iOS 16 every phone reads as "iPhone", so the user names it; empty means the default).
- **EventChannel** `com.rouddy.bluetooth_communicator/bluetooth_events`. Each event is a flat map with a `type` key: `status{advertising, scanning, connectedCount, bluetoothOn}`, `discovered{deviceId, name}`, `connected{deviceId, peerId, name}`, `disconnected{deviceId}`, `peers{peers: [{deviceId, peerId, name, platform, state, connected}]}`, `pairingRequest{deviceId, peerId, name, code, repair}`, `pairingResult{deviceId, peerId, result}`, `peerRejected{deviceId, reason, byPeer}`, `peerUnpaired{deviceId}`, `bonding{deviceId}` (Android only, emitted when `createBond` starts), `bondLost{deviceId}` (the OS pairing was removed on either phone; shown as 페어링 해제됨 until it connects again), `clipboard{deviceId, result, text?, status?}`, `clipboardShared{deviceId}`, `mediaControl{deviceId, op, result, state?, status?}`, `fileTransfer{id, deviceId, peerId, direction, name, size, mime, state, bytes, byPeer, reason?, status?, path?}`, `apps{apps: [{packageName, label, listening, receiveService, registeredAt, lastUsedAt}]}` (Android only: the apps registered with the AIDL service, sent on `initialize` and whenever the list or who can receive changes), `error{message}`, `log{message}` (iOS only: the engine's and CoreBluetooth's decisions, printed by Dart outside release builds, which is how `flutter drive` shows them).
- `connected` means an authenticated protocol session (docs/protocol.md 6.1), not a GATT connection; `name` is the one the peer announced in HELLO. `disconnected` is sent when no session to that device is left, and also when a connect attempt ends without one (so Dart can leave 연결 중).
- `peers` is the full list of app-paired peers, which native code owns (Android: `ble_identity` prefs + Keystore). It's sent on `initialize` and whenever it changes; Dart's 연결 기록 list is built from it and isn't persisted in Dart. `state` is `paired`, `repairNeeded` (the peer answered UNKNOWN_PEER), `badMac`, or `unpairedByPeer`. Only `paired` peers are reconnected automatically.
- App pairing (6.3): when the user connects with `pair: true` to a phone this app has no key for, both phones get `pairingRequest` with the same six-digit `code`, and each user answers with `respondPairing`. An approved request stays pending until the peer approves too; `pairingResult.result` is `paired`, `rejected`, `timeout`, `cannotPrompt`, `mismatch`, `badMac`, or `linkLost`. Pending requests are replayed on `initialize`. Android posts a notification for them when the app isn't in the foreground.
- `peerRejected.reason` is the REJECT reason in lowerCamel (`unknownPeer`, `badMac`, `alreadyConnected`, …). `alreadyConnected` is never sent to Dart (it's routine, 9절).
- Clipboard (`/clipboard`, docs/protocol.md 10절): `requestClipboard` asks the peer for its clipboard text. `clipboard.result` is `waiting` (the peer's app wasn't on screen, so it asked its user; another event follows), then `ok` with `text` (Dart puts it into this phone's clipboard), `empty`, `notText`, `unavailable`, `denied`, `tooLarge`, `timeout` (60 s), or `failed` with the delivery `status` (1/2: the peer's app is too old; 1000: not connected). `clipboardShared` says this phone just sent its clipboard to that peer. `setClipboardSharing` is the 클립보드 공유 setting (default on; Dart replays it on `initialize`); with it off, requests get `denied`. Only the focused app may read the clipboard (Android 10+, iOS): Android answers right away if the app has window focus, else posts a "눌러서 보내기" notification (channel `ble_clipboard`) and answers once the app gets focus (`MainActivity.onWindowFocusChanged` → `ClipboardShare.onFocus`); iOS answers only while active (iOS may ask the user to allow pasting another app's content), else `unavailable`.
- File transfer (`/file`, docs/protocol.md 10절): `sendFile` opens the system file picker (Android `ACTION_OPEN_DOCUMENT`, iOS `UIDocumentPickerViewController`) and offers the pick to the peer; it returns `true` once offered, `false` if the picker was closed, or throws `NOT_PAIRED`, `READ_FAILED`, `BUSY` (a picker is already open). `path` skips the picker (tests). `fileTransfer` describes one transfer, sent on every change (progress too) and replayed on `initialize`: `id` is local (what the other methods take), `direction` is `send`/`receive`, `state` is `offered` (waiting for this user), `waiting` (for the peer's), `transferring`, `completed` (with `path`), `declined`, `canceled` (`byPeer` says who), or `failed` with `reason` (`timeout`, `unsupported`, `notConnected`, `linkLost`, `storage`, `read`, `peer`, `busy`, `unpaired`) and maybe the delivery `status`. The receiver answers with `respondFile`; either side can `cancelFile`. A received file stays (and is replayed) until `dismissFile`; `exportFile{action: save|share}` saves it where the user picks (Android `ACTION_CREATE_DOCUMENT`, iOS Files export; `true` if saved, `false` if canceled) or opens the share sheet, and throws `NOT_FOUND` once it's dismissed. Offers and finished downloads post a notification while the app isn't in the foreground (Android channel `ble_file`).
- Media keys (`/control/media`, docs/protocol.md 10절): `controlMedia` presses `op` (`getState`, `play`, `pause`, `playPause`, `stop`, `next`, `previous`) on the peer's active media player and returns right away; the answer comes as `mediaControl`: `result` is `ok` (with `state`: `playing`, `notPlaying`, or `unknown`), `failed` (the peer couldn't press the key), `unsupportedOp`, `unsupported` (the peer's CAPS leave the path out: an iPhone, or an older Android app), `timeout` (10 s), or `undelivered` with the delivery `status`. Only Android answers (`MediaControl`: `AudioManager.dispatchMediaKeyEvent`, then `isMusicActive()` 600 ms later); iOS can't control other apps' playback, so it only sends and leaves the path out of its CAPS. The device page shows the controls only for non-iOS peers (`peers[].platform`).
- `removeDevice` sends UNPAIR if a session is up (waiting at most 3 s for its ACK), deletes the key and the peer, and then drops every link to the device and cancels pending connects. The peer gets `peerUnpaired` and stops reconnecting.
- Shared GATT UUIDs are hard-coded on both native sides. Service `1F9ED31D-B738-4D4C-A6D8-86DBF0F9C001`; protocol characteristic `002069AC-115D-4391-8772-13E44DF757FC` (changed from the chat's `DB912050-…` so old builds don't connect). It carries protocol frames: the central writes with response, the peripheral notifies.
- Both sides send the same structured `status`, and Dart builds the label (`advertising scanning connected:1`, `idle`, `bluetooth-off`; `unknown` before the first event). `connectedCount` counts peers with a session.
- `initialize` returns a Bool on both platforms. Android returns `true` once it has started the background service, or `false` if the Bluetooth permissions are missing. iOS returns whether the Bluetooth authorization is `allowedAlways`. Runtime permissions aren't part of the channel contract: Dart requests them with `permission_handler` before calling `initialize`.
- `pair` is true only for user-initiated connects (the 연결 button). Android then bonds unbonded devices first via `createBond()` (system pairing dialog), and only such links may start an app pairing. Without it, Android connects only to bonded app-paired peers, so automatic reconnects never prompt. iOS ignores it.
- `deviceId` is the MAC address on Android and the `CBPeripheral`/`CBCentral` identifier UUID string on iOS (the same UUID for one remote phone in both roles, seen with the S23). These IDs are not portable between platforms; `peerId` (a UUID per install) is.
- The protocol code is duplicated in Kotlin (`android/.../protocol/`) and Swift (`ios/Runner/Protocol/`), kept in step: the same structure and names, the same test cases, and `test_vectors/protocol_v1.json` (written by `test_vectors/generate.py` from the spec, as an independent third implementation), which both test suites check byte for byte. Change both together.

When you add a method or event, update `lib/main.dart` (`BleAppController._invoke` / `_handleEvent`), `MainActivity.kt` + `BluetoothBackgroundService.kt` (+ `BleRuntime.onDartEvent` for engine events), and `AppDelegate.swift`.

### Dart (`lib/main.dart`, single file)

- `BleAppController` is a `ChangeNotifier`; each page listens to it (`ListenableBuilder`). It keeps the advertising/central toggles in `shared_preferences` and replays them on `initialize()`; the registered-device list comes from the native `peers` event. Keys from older builds (`prefs_messages`, `prefs_unread_counts`, `prefs_registered_devices`) are deleted on launch.
- Permissions: `BleAppController.checkPermissions`/`requestPermissions` use `permission_handler`. Required permissions are `bluetoothScan`/`bluetoothConnect`/`bluetoothAdvertise` on Android and `bluetooth` on iOS. `notification` is requested on Android but stays optional (it's used for pairing requests in the background). If the user permanently denies a permission, the settings page offers `openAppSettings()`. Once the Bluetooth permissions are granted, the settings page shows them as a status that can't be tapped, plus a separate tile that opens system settings while notifications are off (`notificationsDenied`). While the settings page is open, coming back to the app re-checks the permissions (`refreshPermissions`) and runs `initialize()` if they were just granted. On iOS (Swift Package Manager build), permission_handler enables `PERMISSION_BLUETOOTH` from the `NSBluetoothAlwaysUsageDescription` key in `Info.plist`, so there's no Podfile macro to set.
- The settings page (Android) has a 연동된 앱 section from the `apps` event: each registered app's label, package, and whether it receives now (listener) or also while closed (RECEIVE service). There's no way to remove one by hand: an installed app with a RECEIVE service would register again, so the list follows installs and uninstalls.
- `HomePage` shows the device list (app-paired peers and connected devices under 연결 기록, scan results under 주변 기기). `DeviceControlPage` (link state, connect button, peer ID, delete) is pushed from it. `SettingsPage` is pushed from the home app bar. The device page also has 파일 보내기 and lists our transfers to that peer (progress, cancel). For peers that aren't iPhones it also has 미디어 조작 (previous, play/pause, next, refresh) with the peer's last reported playback state (`mediaStates`). `MyApp` shows a `PairingDialog` (code, 승인/거절, then "waiting for the peer") for each `pairingRequest`, on whatever page is open; it closes itself when the request ends. Likewise a `FileTransferDialog` for each incoming file: the offer (승인/거절), the download's progress, then the export screen (저장, 앱으로 보내기, 닫기 = `dismissFile`); it closes itself when the transfer ends otherwise. Errors, pairing failures, and rejections show as SnackBars. The UI strings mix Korean and English.

### Android (`android/app/src/main/kotlin/.../bluetooth_communicator/`)

- `minSdk` is 31 (Android 12), so the app only uses the `BLUETOOTH_SCAN`/`CONNECT`/`ADVERTISE` runtime permissions and has no location-permission or pre-Oreo code paths. The remaining `SDK_INT` checks are for API 33 (`TIRAMISU`) GATT/parcel APIs.
- `compileSdk` is pinned to 37 because `permission_handler_android` 14.x requires it. `targetSdk` still follows Flutter's default.
- `protocol/` is the protocol of `docs/protocol.md`, in plain Kotlin with no Android dependencies, tested on the JVM (`android/app/src/test/.../protocol`, including `EngineTest`, which connects two engines through an in-memory network on a virtual clock): `Frames` (split by MTU, at most 512 bytes per frame; reassemble per tid), `Records`/`Envelopes` (encodings, TLV), `Crypto` (SHA-256, HMAC, HKDF, AES-GCM, P-256 ECDH, replay window), `FileTransfer` (`/file`: `FileMessage` codec and the `FileTransfers` state machine over the engine; 16 KiB chunks, 3 unacknowledged, sent with `bulk = true`, the lowest frame priority, which a new link with 20-byte frames holds back for up to 3 s until its MTU grows), and `ProtocolEngine`. The engine runs every link: frame scheduling by priority, HELLO, app pairing, AUTH, SEALED sessions, one link per peer, and delivery (ACK, dedup, retransmission, TTL, flow control, CAPS, UNPAIR). It isn't thread-safe; everything calls it on the main looper.
- `BleRuntime` is a process-wide singleton: it owns the engine, the `AndroidPeerStore` (peerId, msgId counter, and peers in `ble_identity` prefs, excluded from backups by `data_extraction_rules.xml`; each pair key K is imported into the Android Keystore as an HMAC key, with a logged prefs fallback if the import fails), and the `AppRegistry`. It implements the engine's host: frames go to the transport (the BLE service while it runs), engine events become Dart events, pairing notifications (channel `ble_pairing`), and `peers` snapshots for AIDL.
- `FileShare` (a singleton like `ClipboardShare`) is the `FileTransfers` host: it reads picked documents through a file descriptor it keeps open for the transfer (so it doesn't depend on the URI grant), writes received files to `cacheDir/received/<time>-<id>/` (checks free space first; deletes them after a day), does all file I/O on one background thread, emits `fileTransfer`, and posts the offer and "received" notifications. `MainActivity` runs the pickers (`onActivityResult`), saves by copying into the created document, and shares through `FileProvider` (authority `<applicationId>.files`, `res/xml/file_paths.xml`).
- `MainActivity` doesn't touch BLE or request permissions. It turns each method call into an `Intent` action (`ble.action.*`) and sends it to `BluetoothBackgroundService` with `startForegroundService`.
- `BluetoothBackgroundService` is a `START_STICKY` foreground service (`connectedDevice` type). It owns advertising (plus the GATT server, opened and closed with it), scanning, and GATT client connections, and carries the engine's frames: a client link starts when its CCCD subscription succeeds, a server link when a central subscribes. GATT callbacks post their work to the main looper. Connections go through bonding: an unbonded device is bonded first (`bondStateReceiver` waits for `BOND_BONDED`) and then connected. User-initiated connects go direct (`autoConnect=false`); automatic ones use `autoConnect=true`, target only bonded peers the engine wants (`shouldReconnect`: app-paired, state `paired`, no live link), and are spaced at least 10 s apart per address. It saves its own toggle state in `ble_service_prefs`, separately from Dart's prefs, so it can restore that state without Flutter running.
- Bonding is what keeps `deviceId` stable. Unbonded phones advertise with rotating random addresses. Once bonded, the stack resolves every later advertisement and incoming connection from that phone to the address it had at bonding time. So scan results, client links, and GATT server peers all report the same ID.
- Two phones with central mode on usually connect to each other twice. The engine keeps one link (9절): it decides when the second link's HELLO arrives, and an established link wins only if it answers a `/ping` within 3 s. Samsung's own services keep the Bluetooth connection up after our app dies, so a dead session otherwise looked alive. The client also re-handshakes on `onServiceChanged` (the peer re-registered its GATT server).
- A client connection whose link the engine dropped while the peer stays linked to our GATT server is kept open, unused (`idleClients`): Android releases the shared connection once no app on the phone holds it as a GATT client, which took the remaining link down. It's reused or closed when that link ends. The ATT MTU is per connection, so both roles use the MTU either side learned (`attMtu`): a central subscribing over an existing connection doesn't renegotiate it. The server also learns it from the writes it gets (`learnMtuFromWrite`: n bytes means MTU ≥ n + 3), since it misses `onMtuChanged` when the exchange happened before it was registered (an iPhone reconnecting right after Bluetooth came back on); a larger MTU reaches the engine as `setMaxFrameSize`.
- The service listens for `BluetoothAdapter.ACTION_STATE_CHANGED`. On power-off it resets its state and drops every link, and the status becomes `bluetooth-off` (iOS reports the same string, and Dart shows a banner). On power-on it runs `restoreStateFromPrefs()`. Each advertising start uses a new `AdvertiseCallback`. The framework keeps the old one across a power cycle, and reusing it fails with `ALREADY_STARTED`. `advertiseCallback != null` marks a start in progress, so overlapping start requests don't create a second advertising set.
- GATT operations run through `GattOperationQueue`, one queue per link and role (`clientQueues`, `serverQueues`). Android allows a single outstanding operation per connection, so the CCCD write, frame writes, and notifications each wait for their callback (`onDescriptorWrite`, `onCharacteristicWrite`, `onNotificationSent`). When a link goes away, its queued operations fail. A callback that hasn't come after 10 s fails that operation and everything queued behind it, since the stack still counts it as outstanding, and the link is closed: a client connection is disconnected and closed (then reconnected if it's an app-paired peer), and a server link is dropped with a `cancelConnection` request, as `closeLink` does.
- `BluetoothBootReceiver` sends `ACTION_RESTORE` on boot.
- `BleEventBus` is a process-wide singleton. It posts events to the Flutter `EventSink` on the main looper, and drops them without a sink (`initialize` replays the state: `BleRuntime.replay`). `MainActivity.cleanUpFlutterEngine` detaches the sink, because the engine dies with the activity without calling `onCancel`. `appInForeground` (onResume/onPause) decides whether a pairing request posts a notification. Resuming clears those notifications.
- **AIDL** (`android/app/src/main/aidl/com/rouddy/bluetooth_communicator/api/`, 11절): `BleCommunicatorService` is exported with action `com.rouddy.bluetooth_communicator.action.BIND`, no permission. `IBleCommunicator` declares the actions, the package, and the result codes as constants. Callers are identified by `Binder.getCallingUid()`: a path must start with one of the caller's packages, and an app is (package, SHA-256 of its signing certificates). `AppRegistry` keeps the listeners, builds our CAPS from them and from apps that declare an `action.RECEIVE` service (refreshed on package changes), checks incoming messages against the sender's CAPS and the local certificate, and delivers them to a listener or by binding the RECEIVE service. `getPeers` only lists peers whose CAPS have the caller's app. The manifest's `<queries>` lists the RECEIVE action for package visibility.
- AIDL `API_VERSION` is 2: `send` returns the message's msgId (taken on the binder thread with `AndroidPeerStore.nextMsgId`, which is synchronized, and handed to `ProtocolEngine.send(msgId = …)`), so the caller has it before the peer's reply, which carries it as `replyTo`, can arrive. A request that fails right away gets an id too. v1 returned a local request id. Other apps copy the `.aidl` files (the Decision model app keeps a copy; `test_app` compiles them from here).
- Registered apps: `AppRegistry` remembers the apps that registered a listener or declare a RECEIVE service in `RegisteredApps` (JSON in the `ble_apps` prefs: package, certificate hash, label, registered/last used time; a different certificate under the same name is a new registration). An app leaves the list when it's uninstalled: the dynamic package receiver (`PACKAGE_REMOVED` without `EXTRA_REPLACING`, `PACKAGE_FULLY_REMOVED`) while the process runs, `PackageRemovedReceiver` (manifest, `PACKAGE_FULLY_REMOVED`, which Android delivers to a stopped process too) while it doesn't, and `reconcile` at startup for what both missed. Removal also drops its certificate cache, queue slots, and RECEIVE binding, and updates CAPS. Package visibility limits what we can see: an app without a RECEIVE service is visible only once it has bound since boot, so after a reboot it's dropped at startup and registers again with its next listener. The list is shown on the settings page (`apps` event).

### test_app (`test_app/`)

A standalone Android app (own Gradle build, AGP 9 built-in Kotlin, no AndroidX) that compiles the communicator's `.aidl` files directly. It lists peers, sends text to `<its package>/chat`, and shows each result; a `ReceiveService` takes messages while the activity is closed. `adb shell "am start -n com.rouddy.bluetooth_communicator.testapp/.MainActivity --es text '…'"` sends to the first connected peer, and results are logged under `TestApp`. ### iOS (`ios/Runner/`)

- `Protocol/` is the Swift port of Android's `protocol/` (CryptoKit for the crypto), tested by `RunnerTests` (codecs, the shared vectors, and the engine on an in-memory network, like Android's `EngineTest`).
- `IOSBleBackgroundManager` (`AppDelegate.swift`) handles the channel stream, owns a `CBCentralManager` and a `CBPeripheralManager` (both with state-restoration identifiers; `UIBackgroundModes` has `bluetooth-central` and `bluetooth-peripheral`), and is the engine's host. Everything runs on the main queue (`MainQueueScheduler` for timers). It saves its toggles in `UserDefaults` (`pref_ios_advertising`, `pref_ios_central`) and the device name in `rbc_device_name`.
- `IOSPeerStore` keeps this install's peerId and each pair key K in the Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`), and the peers and the msgId counter in `UserDefaults`. The Keychain survives uninstalling, so the first launch without the `rbc_installed` flag deletes its items (a reinstall is a new phone, as on Android).
- Central role: a link starts once the notification subscription succeeds (an already-notifying characteristic counts). Frames go out as writes with response, sized by `maximumWriteValueLength(for: .withoutResponse)` (MTU - 3, at most 512) so no write becomes a long write; `didWriteValueFor` reports each. A link can come up before the MTU exchange (20-byte frames, seen right after a reconnect) and CoreBluetooth has no callback for it, so each write reads the length again and passes a larger one to `setMaxFrameSize` (the peripheral role does the same with `maximumUpdateValueLength`). `didModifyServices` for our service (the peer re-registered its server) rediscovers and starts a new handshake. When the peer requires encryption, the first subscribe fails with insufficient authentication/encryption: iOS starts pairing but doesn't retry, so the subscribe is retried every 2 s, up to 30 times. `connectDevice` falls back to `retrievePeripherals(withIdentifiers:)`, and requests before `poweredOn` wait in `pendingConnectIds`. Automatic reconnects (`reconnectPeers`, on power-on, disconnects, and `disconnected` events) issue a pending `connect` (it never times out) for each paired peer the engine has no link to, by the identifier we last reached it under as central (`rbc_peripheral_ids`).
- Peripheral role: the service (characteristic: write, notify, both requiring encryption) is published before advertising starts (`didAdd`). `advertisingStarting` marks a start until `didStartAdvertising`, so the launch's restore and Dart's `setAdvertisingEnabled` don't both start it (the second failed with "already started"); a manager that state restoration hands back still advertising counts as advertising. A subscription starts a link; writes are frames (long writes are refused); frames to the central go out with `updateValue`, queued while the transmit queue is full until `peripheralManagerIsReady` (iOS has no per-notification callback, so a queued notification counts as written). CoreBluetooth can't drop a central; `closeLink` only forgets the link. State restoration revives subscribed centrals (`willRestoreState`) as links waiting for HELLO_c, but such a central still holds its session with the old process and the service didn't change, so it never sends one: once the peripheral manager is powered on, each revived link gets `engine.requestHandshake`, a HELLO_p that makes the central start over (6.5).
- `FileShare.swift` hosts `FileTransfers` (owned by `IOSBleBackgroundManager` as `files`): received files go to `Caches/received/<UUID>/` (deleted after a day), file I/O runs on one serial queue, the picker is `UIDocumentPickerViewController(asCopy: true)` (the copy is deleted when the transfer ends), `save` exports to Files and `share` opens `UIActivityViewController`. Offers and finished downloads post a local notification while the app isn't active; authorization is requested once on `initialize`. Two extra error codes: `NO_UI` (nothing on screen to present from) and `BAD_ARGS`.
- App pairing can only prompt while the app is active (`canPrompt`); otherwise the peer gets REJECT(CANNOT_PROMPT). There's no notification flow on iOS yet.
- The app uses the UIScene lifecycle (`SceneDelegate.swift`). So `window` is still nil in `didFinishLaunchingWithOptions`, and both the plugins and the BLE channels are registered in `didInitializeImplicitFlutterEngine` (`FlutterImplicitEngineDelegate`) on `engineBridge.applicationRegistrar.messenger()`.

## Current state / known gaps

Branch `feature/bluetooth_protocol`. The protocol of `docs/protocol.md` is implemented on both platforms through step 5, plus AIDL (step 7) on Android: framing, app pairing, AUTH, SEALED, one link per peer, delivery, CAPS. Verified between two Galaxy phones (Z Fold5 and S23, Android 17): app pairing from either phone and declining it, reconnects after a force-stop and a Bluetooth power cycle, deletion with UNPAIR, and the test app in both directions (listener and RECEIVE service, 3000-byte messages, delivery after the peer's Bluetooth came back). Verified between an iPhone SE (AlgorigoSE, iOS 27) and the S23/Fold5: app pairing with the iPhone as central and as peripheral, reconnects after either app restarted (the dead session replaced through `/ping`) and after a Bluetooth power cycle, and the iPhone receiving UNPAIR. Keep these gaps in mind:
- Deleting a device on the iPhone (iOS sending UNPAIR) hasn't been tried on a device yet; it's the shared engine logic, covered by the tests.
- iOS receives no app data (no AIDL), so a peer's sends to it fail with NO_RECEIVER, and it can't approve a pairing in the background.
- `flutter drive` uninstalls the app when the test ends (flutter_tools `drive_service.dart`, `stop()`), unless it's run with `--keep-app-running`: the next run installs it fresh (permission prompts again, peers and peerId gone). On iOS, a build installed with `xcrun devicectl device install app` and started with `devicectl device process launch --terminate-existing --console` runs the integration test without a driver, and `--console` shows the native `[BLE]` logs.
- File transfer (`/file`) was verified between the Z Fold5 and a Galaxy Jump3 (SM-M446K): both directions with matching checksums (about 6.5 KB/s when the central sends, 12 KB/s when the peripheral does), the offer and "received" notifications with the app in the background, 저장 (document picker) and 앱으로 보내기 (share sheet), decline, and cancel from either side; an older peer without `/file` is refused through its CAPS. Between the Z Fold5 and the iPhone SE (AlgorigoSE), both directions with the iPhone as central and as peripheral (`CENTRAL=false`), with matching checksums: iPhone central sending 6.8 KB/s, receiving 300 KB at 15 KB/s and 1 MB at 26 KB/s; iPhone peripheral sending 25 KB/s, receiving about 7 KB/s. Not tried on the iPhone yet: its picker and export screens (they need a person) and its background notifications (the test iPhone was in Sleep Focus). A link loss mid-transfer (the Fold5's Bluetooth turned off and on while 1 MB went to the iPhone) recovered five times out of five, with matching checksums, sometimes after an extra disconnect (below). There's no resume: a transfer that loses its link for longer than the chunk TTL (60 s) fails.
- Branch `feature/decision`: AIDL v2 (msgId from `send`, for replies) and the registered-app list, built for the Decision model app (another repo), which runs questions on the model loaded on a paired phone. Verified between the Z Fold5 (serving d3-lite) and the Galaxy Jump3: requests and replies both ways, the serving app started through its RECEIVE service, and uninstalling `test_app` with the communicator running and with its process dead.
- `/control/media` (remote media keys) was verified with the iPhone controlling VLC on the Z Fold5 (state, pause, and play answered in 0.2–0.9 s), the Fold5's page for the iPhone showing no media controls, and the Jump3 on an older build getting the update message. Next/previous and stop weren't checked against a real playlist.
- Android acknowledges a notification (`onNotificationSent`) once it's queued, and while its ATT channel is congested (more than about 200 queued) it drops the responses to the peer's writes; an iPhone then gives up on the write after 30 s and disconnects. That's why the engines hold bulk records on a new link with 20-byte frames until its MTU grows (at most 3 s). A `/ping` counts any authenticated record from the peer as its answer, since the ACK can wait seconds behind file chunks the peer already queued (TODO.md 34).
- A link that hears nothing from its peer for 60 s sends a `/ping` and is dropped after 10 s without an answer, so a dead session left by a Galaxy holding the connection no longer blocks reconnects (TODO.md 33). The case itself didn't reproduce on the devices at hand (force-stopping the Jump3's app dropped the connection); the engine tests cover it.
- On both platforms the protocol characteristic and its CCCD require an encrypted link. An unbonded central gets "insufficient encryption" (iOS centrals then pair automatically) instead of talking under a rotating random address.
- `BLUETOOTH_SCAN` must keep `neverForLocation`. Without it, Android 12+ silently delivers zero scan results because the app doesn't hold location permission.
